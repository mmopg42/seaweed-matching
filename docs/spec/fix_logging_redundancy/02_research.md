## 2. Detailed Findings

### 2.1 Q1: Why are redundant log files being created while the session file remains empty?

**Method**: Code review of `App.xaml.cs` and `Infrastructure/Logging/FileLoggerProvider.cs`.

**Findings**:
- `App.xaml.cs` initializes the logger with a path like `.../Logs/20260113/ChronoView_Debug_20260113_153835.log`.
- `FileLogger.Log` (the actual sink) performs the following logic on EVERY log call:
  1. Takes the initialization path: `ChronoView_Debug_20260113_153835.log`.
  2. Extracts `baseName` by finding the LAST underscore: `ChronoView_Debug_20260113`.
  3. Appends today's date: `_20260113`.
  4. Final filename: `ChronoView_Debug_20260113_20260113.log`.
- This explains why logs go to a new file, while the original file (opened by `App.xaml.cs` for the header) never receives subsequent logs via the `ILogger` interface.

**Evidence**:
- `App.xaml.cs:192`: `var logFile = Path.Combine(dateFolder, $"ChronoView_Debug_{startTime:yyyyMMdd_HHmmss}.log");`
- `FileLogger.cs:80`: `var baseName = fileName.Substring(0, fileName.LastIndexOf('_'));`
- `FileLogger.cs:90`: `var todayLogFile = Path.Combine(todayDateFolder, $"{baseName}_{today}.log");`

**Conclusion**: The logic in `FileLogger.Log` is redundantly re-dating a file that is already dated.

---

### 2.2 Q2: Does the current implementation handle date transitions correctly?

**Method**: Analysis of `FileLogger.cs` logic.

**Findings**:
- The logic *attempts* to handle date transitions by checking `DateTime.Now.ToString("yyyyMMdd")` on every log call and creating a folder if it doesn't exist.
- However, by forcing a new filename every time the date changes, it would split a single session's logs into multiple files if the session spans across midnight.
- Currently, it's just broken because it's suffixing the date *twice*.

**Conclusion**: We should decide whether session logs should span across files or stay in the session-initiated file. Given the requirement for session-specific files (`HHmmss`), staying in the same file is usually preferred for a single session, or the logic should be smarter about transitions.

## 4. Options Analysis

### Option A: Use the initialization path directly
**Description**: Fix `FileLogger` to simply use the `_logFilePath` passed in the constructor.
**Pros**: Simplest fix. Respects the session filename generated by `App.xaml.cs`.
**Cons**: If the app stays open for days, everything still goes into the same file named with the start date.

### Option B: Fix the "smart" path calculation
**Description**: Change how `baseName` is extracted (e.g., look for the first 2 underscores `ChronoView_Debug`) and ensure it only appends the date if it's not already there or if the date truly changed.
**Pros**: Maintains daily folder organization even for long-running sessions.
**Cons**: More complex logic, might still conflict with the `HHmmss` session naming.

## 5. Recommendations

### Primary Recommendation
Implement **Option A** with a slight modification: allow the logger to just use the path it was given. `App.xaml.cs` already ensures the folder exists. If date transition is a concern, `App.xaml.cs` should be the one managing the "current" log file or `FileLogger` should be passed a *directory* and a *prefix* rather than a full path if it wants to be responsible for the filename.

However, the user explicitly wants the `HHmmss` log to work. So **Option A** is the most direct solution to the user's request.
